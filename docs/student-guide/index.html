0.3 Log the GitHub CLI into your account

This lets Cursor create a GitHub repository and push your code without you touching GitHub's website. Open a terminal (on Mac: the Terminal app; on Windows: PowerShell) and type:

gh auth login
  1. It asks "Where do you use GitHub?". Choose GitHub.com with the arrow keys, press Enter.
  2. "Preferred protocol": choose HTTPS.
  3. "Authenticate Git with your GitHub credentials?": Yes.
  4. "How would you like to authenticate?": Login with a web browser.
  5. It shows a one-time code like ABCD-1234. Copy it, press Enter, the browser opens, paste the code, click Authorize.
  6. Back in the terminal you'll see "Logged in as yourname". Done.
Check yourself

Part 1Cursor from zero

Cursor is a code editor, like VS Code (it's actually built on VS Code), with an AI agent built in. You talk to the agent in plain English. It reads your files, writes code, runs commands in the terminal, opens a browser to test your app, and tells you what it did.

The mental shift: you're not the typist anymore. You're the person who decides what to build and checks that it's right. Cursor does the typing.

1.1 Install and sign in

  1. Open the Cursor installer you downloaded in Part 0 and finish the install.
  2. Open Cursor. It asks you to sign in. Click it, the browser opens, sign in (Google or GitHub is easiest), then come back to Cursor.
  3. You may see a few setup screens (theme, shortcuts). Keep the defaults; the exact screens change between versions. If you already use VS Code, you can bring your settings over later from Cursor Settings → General → Account → VS Code Import.
  4. You'll land on a welcome screen. That's it, Cursor is ready.
Plans and money

Cursor's Free plan includes the agent and Tab autocomplete with limited usage and Cursor's own models. A full build like this one may run past the free limit. Paid plans (Plus, Premium and up) give more usage and more models. Cursor's old student discount closed to new sign-ups on 25 June 2026, so don't count on it. Check cursor.com/pricing for current details before you pay for anything.

1.2 Make a project folder and open it

Cursor always works inside one folder. Everything the agent creates goes inside it. So first make an empty folder.

  1. In Finder (Mac) or File Explorer (Windows), go to Documents and create a new folder. Name it something with no spaces, like ai-interview-coach.
  2. In Cursor, click File → Open Folder… (on the welcome screen there's also an Open project button).
  3. Pick your new folder and click Open. If Cursor asks "Do you trust the authors of the files in this folder?", click Yes, I trust the authors. It's your own empty folder.
  4. Drag your prd.md file (from Part 2) into this folder. You'll see it appear in the left sidebar.

1.4 Talk to the agent

  1. Open the Agent panel if it isn't open: ⌘ Cmd+I on Mac, Ctrl+I on Windows.
  2. Click in the text box at the bottom of the panel.
  3. Type what you want in normal English. Long, messy, detailed messages are fine. Look at my prompts in this guide: they read like someone talking, typos and all, and they worked. You can also dictate: ⌘ Cmd+Shift+Space starts voice input.
  4. Press Enter to send. (Shift+Enter adds a new line without sending.)
  5. Watch. The agent shows each step: which files it reads, what it edits, which commands it runs. It ends with a summary of what it did.
  6. Reply in the same box to continue. Each conversation is called a chat. Start a fresh chat with the + button at the top of the panel (or ⌘ Cmd+N) when you switch to a new topic.
Real trick from that night

You can run two chats at the same time. At 9:42 one chat was building my backend. At 9:43 I opened a second chat and asked it to write the Google Stitch prompt. Both worked in parallel. Click + for a new chat; your old chats stay in the chat history.

1.5 The four modes

Click the mode picker (number 5 in the diagram) under the text box, or press Shift+Tab in the chat box to cycle through the modes. You'll see these four. Picking the right one is the single most important Cursor skill.

Agent does the work

The default. Reads files, writes and edits code, runs terminal commands, tests things. Use it when you know what you want and want it done.

"Can you run this application for me, I want to test it locally."

Plan thinks first

Researches your code, asks you clarifying questions, then writes a step-by-step plan with a to-do list. It does not change your code until you click Build. Use it for any big feature.

"Build the backend from this PRD." · "Build the frontend from these designs."

Ask read-only

Answers questions about your code or a concept. It reads but never changes files. Use it to learn and explore safely.

"Explain what render.yaml does, line by line."

Debug finds the bug

For bugs you can't figure out. It forms guesses about the cause, adds temporary logging, asks you to reproduce the bug, then fixes it based on what the logs show.

"After I submit, the results page doesn't respond to clicks."

Which mode should I use?

1.6 Plan mode, step by step

I used Plan mode for every big step that night: backend, frontend and AI. Here is exactly what happens:

The Plan → Build loop
  1. Switch the mode picker to Plan.
  2. Type your request and attach context (see 1.7). Send it.
  3. Cursor reads around, then shows clickable questions. These are real decisions, not small talk. For my backend it asked three: free or paid Render plan, create a new GitHub repo or not, and how many questions to put in the bank (54, 108 or 180). Each had a "Recommended" option.
  4. Click your answers and submit.
  5. Cursor writes a plan: a Markdown document with the folder layout, the design decisions, diagrams and a to-do list. It opens in the editor.
  6. Read the plan. This is your job. You can edit the plan file directly, like any document, or reply in the chat ("don't use UUIDs", "also deploy to Vercel after testing") and it updates the plan. I did this once: I asked it to add "test locally, push to GitHub, deploy on Vercel" to the frontend plan before building.
  7. Click Build. Cursor switches to building, ticks off each to-do as it goes, and reports back at the end.

Plans are saved in your home folder by default, so they survive after the chat ends. If you want the plan inside your project (to share with teammates), click Save to workspace.

Why bother planning?

My backend plan noticed something I hadn't thought about: Render's free tier wipes its disk on every restart, so saved interview sessions would vanish. It asked me before writing any code.

1.8 Model picker: leave it on Auto

Next to the mode picker is the model picker (number 6). Auto lets Cursor pick a model for each request, balancing quality and cost. I used Auto for everything in this guide. Auto isn't included on every plan; if you don't see it, keep whatever model is selected by default. As a beginner you don't need to think about models at all.

1.9 Review changes, and how to undo

Cursor edits files directly, but you stay in control:

  • Changed files are listed at the bottom of the agent panel after each turn. Click a file to see the diff: green lines added, red lines removed.
  • Keep or undo. You can keep or undo (reject) changes per file, or all at once, using the buttons in that review area.
  • Checkpoints. Hover over one of your earlier messages and you'll see a Restore checkpoint option. It rolls your files back to how they were at that point (the chat messages stay). Your safety net when the agent goes in the wrong direction. Checkpoints are separate from Git, so they also work before you've ever committed.

1.10 When the agent wants to run a command

The agent runs terminal commands all the time: pip install, npm run build, starting servers. Cursor decides which ones need your OK. The setting lives in Cursor Settings (⌘ Cmd+Shift+J) → Agents → Approvals & Execution:

  • Auto-review (the default): safe commands run straight away, and risky ones are checked first or stopped for your approval.
  • Allowlist: only commands you've approved before run without asking.
  • Run Everything: no questions asked. Don't use this as a beginner.

When the agent does stop and show you a command, read it before you approve. Installing packages, running tests and starting servers are normal. Deleting files outside your project is not. Opening and clicking in the built-in browser also asks for approval by default.

1.11 Rules: instructions Cursor always follows

If you keep telling Cursor the same thing ("use TypeScript", "always write tests"), put it in a rule instead:

  • Project rules live in your project, in a .cursor/rules/ folder, or in a file called AGENTS.md. Our frontend has an AGENTS.md telling the agent to read the Next.js docs before writing code.
  • User rules apply to all your projects. Set them under Customize → Rules in the sidebar.
  • Easiest way to make one: type /create-rule in the chat and describe the rule.

You don't need rules to start. Add them when you notice yourself repeating something.

Part 2Research and the PRD

A PRD (Product Requirements Document) is a plain description of what you're building: who it's for, what screens it has, what data it stores, which technologies, and where it'll be hosted. It's the single most important input to Cursor. A vague PRD gets you a vague app.

I didn't write mine from scratch. I did the research in ChatGPT and had it produce the PRD.

2.1 Research in ChatGPT

  1. Open chatgpt.com. If you have the option, turn on Deep research or web search so it looks at real products, not just its memory.
  2. Ask it to research the problem and what already exists. Example prompt below.
  3. Read what it gives back. Push back where it's generic ("which of these complaints come from Indian students specifically?").
I want to build a web app that helps CS students practice technical interviews with multiple-choice questions across DSA, system design, Python, Java, JavaScript, React, Next.js and FastAPI. Research what tools already exist, what students complain about, and what a simple first version (MVP) should include. Keep it practical: this is a student capstone project.

2.2 Turn the research into a PRD

In the same ChatGPT chat:

Now write a detailed PRD in Markdown for the MVP. Include: product vision, problem statement, target users, every screen and what's on it, user flow, data model (tables and columns), API endpoints, folder structure for a monorepo, and tech stack: Next.js + TypeScript + Tailwind for the frontend, FastAPI + SQLAlchemy + SQLite for the backend. Frontend will be hosted on Vercel, backend on Render free tier, code on GitHub. No login for the MVP: the user just enters their name. Include a "future scope" section for AI-generated questions.
  1. Copy the full Markdown output.
  2. Open a plain-text editor, or create a new file in Cursor: File → New File, paste, save as prd.md inside your project folder.

My PRD had these sections, so check yours has something similar: project overview, target audience, features (name entry, subject selection, interview config, MCQ screen, results, review), data model, API list, folder structure, deployment, and future scope.

Watch out

Say where you'll host things, in the PRD. Cursor made different choices because it knew we'd use Render's free tier, like reloading the question bank on every boot because the free disk gets wiped.

Part 3Build the backend with Plan mode

I built the backend first and told Cursor to leave the frontend empty, because my designs weren't ready yet. You don't have to do it in this order, but it worked well: the designs could then be made to match the real API.

3.1 Two things to understand first: monorepo and GitHub

A monorepo is one project folder holding both the frontend and the backend. GitHub stores a copy of that folder online. Render and Vercel both watch the same GitHub repository: every time new code is pushed, they rebuild automatically.

How code travels from your laptop to the internet

You don't need to type git commands. Cursor runs them for you, as long as you did the gh auth login step in Part 0.

3.2 Send the backend prompt

  1. Make sure prd.md is in your project folder and the folder is open in Cursor.
  2. Open the Agent panel, click + for a new chat.
  3. Set the mode picker to Plan.
  4. Type the prompt below. Where it says @prd.md, type @ and pick the file from the menu so it's attached properly.
  5. Press Enter.
Okay there is a PRD, I am attaching PRD.md file. It has all the requirement of what we are trying to build. For now, I want you to focus on building MVP, okay? You will not be touching the frontend. You will only work on the backend. Frontend, you just keep a placeholder, that's it. Nothing, no components, nothing should be built. The reason is I am getting the design done. Once the design are done, I will share you the screenshot and the design. After that, we will start building the frontend. So, we'll be using Monorepo, all the information is available in PRD file. Also, remember that we'll be hosting this on backend on render and frontend on Vercel, and we'll be pushing this into a GitHub repository. So, based on this I want you to start implementing, finish the backend and put the basic structure for frontend. Once I give you the design, you will start working on the design. @prd.md

Look at what's in there. Nothing technical. It says what (backend MVP), what not (no frontend components), why (designs are coming), and where it'll live (Render, Vercel, GitHub).

Part 4Design the screens with Google Stitch

While the backend was building, I opened a second chat to work on the design. Google Stitch is an AI tool that turns a text description (and reference images) into screen designs and HTML code.

Design loop

4.1 Let Cursor write the Stitch prompt

Why ask Cursor and not write it yourself? Cursor has read your backend. It knows the exact screens, the fields the API returns, the error cases. So the designs come out matching what your backend can actually do.

  1. Click + for a new chat. Keep the mode on Agent (or Ask; it only needs to read).
  2. Send this:
Now you have the idea what we are trying to build. So now I want you to generate a prompt which I will be giving to Stitch for building an AI interviewer frontend. So this will help it to build the frontend. You have the idea what we are building backend, you know all the APIs and everything. So give me a prompt which I can give Google Stitch to design my frontend.

It came back with a long prompt (about 1,300 words) describing all 8 screens, every loading and error state, sample data, and the design style. The full prompt is in the appendix so you can reuse it.

4.2 Generate the designs in Stitch

  1. Go to stitch.withgoogle.com and sign in with your Google account.
  2. Choose the web app option (not mobile) when it asks.
  3. Find a reference image of a look you like. I wanted glassmorphism (frosted-glass panels, soft blurred colours), so I used a screenshot of a design in that style. Pinterest, Dribbble and Mobbin are good places to look.
  4. Upload the image with the image/attach button in Stitch's prompt box.
  5. Paste the prompt from Cursor and add one line about the image, like "Use the attached image as the visual style: glassmorphism."
  6. Generate. Stitch creates the screens. You can ask for changes in the same box ("make the buttons black", "add a step indicator").
  7. When you're happy, select the screens and export / download them. You get a folder per screen with a screen.png (the picture) and a code.html (the HTML), plus a DESIGN.md with the colours, fonts and spacing.
  8. Unzip it somewhere you can find it. Mine was Downloads/stitch_ai_interview_coach_webapp.

Part 6Connectors: let Cursor control Render and Vercel

Out of the box, Cursor can edit files and run commands on your laptop. It can't log into your Render or Vercel account. A connector fixes that.

The technical name is MCP (Model Context Protocol). An MCP server is a small bridge that gives Cursor a set of tools for one service, like "create a web service on Render" or "read the Vercel build logs". In Cursor, these come packaged as plugins.

What a connector does

Honestly, I first asked Cursor to deploy with no connector. It opened the Render website in its built-in browser and asked me to log in so it could click through. Then I asked:

Can we use some connector or MCP of render dot com available to host it?

Cursor checked Render's docs and told me how to add it. Here are the steps.

6.1 Add the Render connector

  1. In the Cursor chat box, type /add-plugin render and press Enter.
  2. A small window appears. Keep the default choice and click Add plugin.
  3. Sign in when Cursor asks (the button says Authenticate or Connect). If it doesn't ask: click Customize in the sidebar → MCPs, find Render, and click its sign-in button there.
  4. A Render sign-in page opens in your browser. Click GitHub, log in, and click Authorize. This also creates a free Render account if you don't have one.
  5. Back in Cursor, Render should show as connected (a green dot or a list of tools).

6.2 Add the Vercel connector

Same steps, with Vercel:

  1. Type /add-plugin vercel and press Enter.
  2. Click Add plugin, then Authenticate.
  3. Sign in to Vercel in the browser (Continue with GitHub) and approve access.

Then tell Cursor you're done:

I am done please help me deploy both frontend and backend
Read this before you connect anything

A connector gives Cursor real control of that account: it can create services, change settings, redeploy. That's why it's useful, and also why you should only connect accounts you're OK with the agent touching. Cursor told me this itself before I connected. You can remove a connector any time from Customize in the sidebar.

If /add-plugin doesn't work in your version, there are two other ways in:

  • Click Customize in the sidebar, search for Render or Vercel, click Install, and pick user scope so it works in all your projects.
  • Browse cursor.com/marketplace. Render and Vercel are both official plugins there.

If a connector shows errors, open the Output panel (⌘ Cmd+Shift+U) and pick MCP Logs from the dropdown. Or just ask the agent: "The Render connector isn't working. Check the MCP logs and tell me why."

Part 7Put the backend on Render

Order matters here, and it confuses everyone the first time, so look at this diagram slowly. The frontend needs the backend's address. The backend needs the frontend's address (to allow it in). So one has to go first.

The order of deployment (the chicken-and-egg problem)

7.1 What Cursor did on Render

With the connector, I didn't click anything on Render's site. Cursor:

  1. Listed my Render workspaces (I had one, "My Workspace") and checked it was empty.
  2. Created a Blueprint from the render.yaml file in the repo. A blueprint is a recipe: "this is a Python web service, the code is in backend/, install with this command, start with that command, use the free plan".
  3. Checked that the blueprint would only create one free service, then approved it.
  4. Waited for the build (2 to 4 minutes), checked the health endpoint, and confirmed all 9 subjects came back.

My backend went live at https://ai-interview-coach-api-dz7u.onrender.com.

Why only the blueprint route is free

Cursor found that the connector's simple "create web service" tool only offers paid plans (cheapest about $7/month). The blueprint route reads render.yaml, which says plan: free. If you ask for free hosting, say so clearly in your prompt, like I did: "it has to be on the free tier".

7.2 Doing it by hand instead (if your connector doesn't work)

  1. Log in at dashboard.render.com.
  2. Click New + → Blueprint.
  3. Connect your GitHub account if asked, and give Render access to your repository.
  4. Pick your repository. Render finds render.yaml and shows the service it will create. Check it says Free.
  5. It asks for the values of CORS_ORIGINS and CORS_ORIGIN_REGEX. For now put http://localhost:3000 in CORS_ORIGINS and leave the other empty.
  6. Click Apply / Deploy Blueprint. Wait for the status to turn Live, then open your-url.onrender.com/api/health.
Free plan facts you must know
  • It falls asleep. After 15 minutes with no visitors, a free Render service shuts down. The next visitor waits about a minute while it wakes up. Open your site a minute before a demo.
  • It forgets. The free disk is wiped on every restart or redeploy. Our app reloads its 108 questions on every boot, so questions are safe, but completed interview sessions disappear. To keep them, you'd need a paid disk or a real database like PostgreSQL.

Part 8Put the frontend on Vercel

This is where the connector hit a wall, and where you'll see the three human moments.

8.1 What happened

  1. Cursor checked which Vercel account the connector was logged into (it was my other email) and tried to create the project.
  2. Vercel said no: the connector was signed in but didn't have access to my personal project space. Cursor generated an approval link, opened it in the browser panel inside Cursor, and asked me to log in to Vercel and click Approve within 10 minutes.
  3. I logged in, approved, and typed: "vercel is connected deploy again".
  4. Cursor created the Vercel project with Root Directory set to frontend, and added the environment variable NEXT_PUBLIC_API_URL = my Render URL.
  5. It noticed two settings that would have bitten me: Vercel's login protection was on for all deployments (students would have seen a Vercel login page instead of my site), and Node.js was set to a different version than the one it had tested on. It switched protection to Standard and Node to 22.
  6. It deployed, confirmed octeveaiint.vercel.app showed my app (not someone else's with the same name), then went back to Render and set CORS_ORIGINS to the Vercel URL and redeployed.
  7. Finally it ran a full test interview against the live backend, pretending to be the Vercel site.
The three human moments

Remember I asked you to keep count? Here they are. Every one was a login or a permission:

  1. Clicking Authenticate and logging in for the Render connector.
  2. Clicking Authenticate and logging in for the Vercel connector.
  3. Logging in to Vercel in the browser panel and clicking Approve on the team access page.

Cursor can't type your passwords, and you shouldn't give them to it.

8.2 Doing it by hand instead

  1. Log in at vercel.com. Click Add New… → Project.
  2. Under Import Git Repository, find your repo and click Import. If it's not listed, click to adjust GitHub app permissions and give Vercel access to that repo.
  3. Root Directory: click Edit and choose frontend. This is the step everyone forgets in a monorepo. Vercel then detects Next.js on its own.
  4. Open Environment Variables. Name: NEXT_PUBLIC_API_URL. Value: your Render URL, like https://your-api.onrender.com (no slash at the end).
  5. Click Deploy. Wait 1 to 2 minutes.
  6. Copy your .vercel.app URL. Go back to Render → your service → Environment, set CORS_ORIGINS to that URL, save. Render redeploys.
  7. If your site shows a Vercel login page to other people: Vercel project → Settings → Deployment Protection → set Vercel Authentication to Standard Protection.
What is CORS, in one paragraph

Browsers block a website from calling a backend on a different address unless the backend says "I allow that website". CORS_ORIGINS is the backend's guest list. If your live site loads but shows "can't reach server" or nothing loads, the guest list is the first thing to check.

After this, updates are automatic. Every time Cursor pushes to GitHub, Render and Vercel rebuild within a few minutes.

The rule

Anything starting with NEXT_PUBLIC_ is sent to every visitor's browser. Anyone can read it. So the Gemini key goes only on the backend (your backend/.env and Render's Environment page), never on Vercel and never with a NEXT_PUBLIC_ name. The browser asks your backend; your backend asks Gemini.

To add the key on Render by hand: Render dashboard → your service → Environment → Add Environment Variable → key GEMINI_API_KEY, value: your key → Save Changes. Render redeploys with it.

What I don't know yet: how well a free Gemini quota holds up with a full class of you hitting it at the same time. That's what the bank fallback is for. We'll find out.
